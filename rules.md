# Vaster LLM Virtual Machine Ecosystem — Core Architectural Rules

## 1. Scope Boundary: Language Coupling & Independence
- **AST Frontend (`vaster_ast`, `vaster_domain`, `vaster_compiler`)**: It is **completely acceptable** for the AST compiler frontend to depend on Dart and Dart VM features (e.g., Dart generic classes, Flutter-style `ComposableNode`, `BuildContext`, `Provider<T>`, and exhaustive Dart `sealed class` pattern matching). AST construction and compilation is a host-side developer frontend API.
- **CRITICAL BOUNDARY — Compiler Frontend Isolation**: The compiler frontend packages — `vaster_ast`, `vaster_domain`, and `vaster_compiler` — **MUST NEVER** be imported by or added as a dependency (production or dev) to any runtime, ISA, VM, continuation, or backend package (`vaster_instruction`, `vaster_runtime`, `vaster_vm`, `vaster_continuation`, `vaster_continuation_manager`, `vaster_model_*`, `vaster_filesystem_*`, `vaster_sandbox_*`, `vaster_agent_*`, `vaster_session_*`, `vaster_context_*`, `vaster_resources`, `vaster_events`, `vaster_policy`, `vaster_policy_engine`, `vaster_budget`, `vaster_scheduler`, `vaster_tool`, `vaster_tool_manager`). All runtime engines operate exclusively on compiled `VasterProgram` bytecode — they must never reference AST nodes, domain spec types, or compiler classes. Tests and examples in runtime packages must construct `VasterProgram` instances directly using low-level ISA instructions from `vaster_instruction`.
- **Pure Serializability**: The target bytecode ISA (`VasterProgram`, `VasterInstruction`), domain specifications (`PipelineSpec`, `AgentRole`), and model descriptors (`ModelDescriptor`) must remain 100% language-agnostic and JSON-serializable so the compiled program can be executed on runtimes implemented in any host language (e.g., Rust, Go, C++, Python).
- **Handles & Descriptors**: Execution engines and ISA opcodes must operate strictly via descriptors, handles, primitive strings, integer registers, and JSON payloads rather than host language object references.
- **The `vaster_vm_api` Boundary**: `vaster_runtime` programs against the `VasterVirtualMachine` interface (`vaster_vm_api`) and **must never** depend on `vaster_vm` (the engine) in production code — the engine depending on the runtime is the only allowed direction (dev-dependency cycles for integration tests are acceptable). Host-facing verbs (`submitProgram`, `runScheduledJobs`) live on `VasterVMEngine` only, never on the interface: the runtime never schedules jobs, only hosts do.
- **Capability Facets Narrow the Seam**: only the runtime *engine* programs against the master `VasterVirtualMachine` interface. Every other collaborator holds the narrowest capability facet its contract uses — `PromptFunnel` for the model-turn verbs, `ToolLoopHost` for the tool loop — declared in `vaster_vm_api` and implemented by the master interface, so a component's constructor type documents what it can actually do. A new VM-facing collaborator gets an existing facet or a new *client-owned* role interface (ISP: the facet is named for the client's job, not the provider's structure), never the master one; facets are also how consumer packages avoid depending on subsystem-manager packages (facet members are accessed, never named — Rule 7 stays quiet). Test doubles implement the facet: a fake that needs a member the facet lacks is the type system reporting scope creep.
- **ABI Naming Conventions Have One Home**: Cross-layer register/session naming rules live exactly once — sibling-register suffixes in `vaster_instruction`'s `register_conventions.dart` (`hitlStatusRegister`, `decideRationaleRegister`) and agent-session naming in `AgentDescriptor.sessionIdFor`. The AST may import an ABI *name* it must agree on with the runtime via a narrow `show` import; this is the sole sanctioned AST → ISA touchpoint and must never widen into type usage.

## 2. Aggressive Composition Over Inheritance
- **Composition First**: Always prefer **aggressive composition over inheritance** across all package abstractions.
- **Composable AST Nodes**: High-level workflow constructs must use composition (`ComposableNode.build(BuildContext context)`) to assemble modular sub-trees rather than deep object inheritance hierarchies.
- **Subsystem Decoupling**: Build complex VM engines by composing decoupled, single-responsibility subsystem managers (`SessionManager`, `ContextManager`, `FileSystemManager`, `ToolManager`, `SandboxManager`, `AgentManager`, `ModelRegistry`, `RuntimeEventBus`, `AgentMessagingHub`, `ResourceTracker`) rather than monolithic superclasses.
- **No Parallel Bookkeeping Maps**: When a component tracks several facts about one entity (state, tree links, queues), compose them into **one entry object per entity** (e.g. the agent manager's `_AgentEntry`) instead of parallel maps that must be mutated in lockstep.
- **Statics Are for Constants and Conventions, Not Behavior**: static members are sanctioned only for canonical constants, pure naming/derivation conventions (`kvFrameName`, `KvStateImage.engineTagOf`), and const builtin instances of instance classes (the `PricingCatalog.builtin` idiom — `CalibrationCatalog.builtin` follows it). Behavior — **especially parsing, codecs, prompt composition, and registries** — lives in (const-constructible) instance classes injected via constructor parameters with canonical defaults (Rule 5), so it can be composed, swapped, and tested in isolation (`KvStateImageCodec`, `SidecarEnvelopeCodec`, `LlamaPromptComposer`). When writing a codec, split the parsed VALUE (accessors/views) from the CODEC (parse/encode/layout): the codec is the external class.
- **Sealed Outcomes Over Boolean Blindness**: Model operation results and lifecycle states as **sealed class hierarchies carrying their data** (`ExtractOutcome`, `AgentLifecycle`) rather than bool/enum + side-channel strings. Exhaustive switches make new shapes impossible to ignore silently; tolerance without observability is forbidden — a tolerated failure must still surface as typed data or a warning event.

## 3. Package Purity & Minimal Core Footprint
- **Lean Core Runtime**: Keep core execution packages (especially `vaster_runtime`, `vaster_instruction`, and `vaster_vm`) clean, lean, and unpolluted by peripheral features.
- **Dedicated Subsystem Packages**: New subsystem capabilities (such as continuation persistence, disassembly, sandboxing, models, and manager components) **must be created as dedicated, single-responsibility packages** (e.g. `vaster_continuation`, `vaster_dis`, `vaster_sandbox_process`, `vaster_model_google_ai`). Do not bloat core execution runtimes with optional features.

## 4. The LLM VM Execution Triad (Model, Session, Continuation)
- **Model = Processor**: `VasterModel` is the non-deterministic LLM compute unit. It consumes structured prompts/messages and tool definitions to produce outputs.
- **Session = Memory & Context Heap**: `VasterSession` maintains conversational turn history, system instructions, pinned context regions, tool schemas, and token tracking. It can be forked (`ForkSessionOp`) to branch memory trees.
- **Continuation = Execution Snapshot**: `VasterContinuation` is identity metadata plus the whole-machine `MachineSnapshot` (Rule 8) — it never enumerates individual pieces of machine state, so it cannot be missing one. It allows long-running or pauseable workflows to yield without blocking host OS threads and resume safely across server reboots.

## 5. Strict Construction-Time Ownership (Runtime & Backend Packages)

This rule applies to all runtime and backend packages (`vaster_runtime`, `vaster_vm`, `vaster_agent_*`, `vaster_session_*`, `vaster_context_*`, `vaster_model_*`, `vaster_filesystem_*`, `vaster_sandbox_*`, `vaster_tool_*`, `vaster_resources`).

- **No Optional Dependencies on Method Signatures**: If a component *owns* a dependency (e.g. a `ResourceTracker`, `ToolManager`, or `ContextManager`), that dependency **must be a required constructor parameter**, never an optional parameter on a method. Optional parameters on method signatures signal unclear ownership and are forbidden for owned concerns.
- **Required Over Nullable**: Prefer `required T field` over `T? field`. If a component always needs a concern, make it required. If truly unlimited/no-op behaviour is needed, provide a canonical default instance (e.g. `ResourceTracker(quota: ResourceQuota.unlimited)`) rather than accepting `null`.
- **Behavioral Configuration Belongs in Descriptors**: Behavioral limits and policies (e.g. `maxToolCallLoops`, `allowedToolNames`) belong in the component's **descriptor** (e.g. `AgentDescriptor`), not as per-invocation parameters.
- **Per-Invocation Exception — `CancellationToken` Only**: The sole legitimate optional per-invocation parameter is `CancellationToken?`. Cancellation is inherently tied to a specific call, not to the component's lifetime, and cannot be set at construction time.
- **Ownership Table**: Every parameter must have an unambiguous owner. When adding a new parameter, answer: *"Does this belong to the component's identity/config (→ constructor or descriptor), or is it truly per-call (→ method parameter only if CancellationToken-like)?"*
- **No `late final` Collaborators**: Build the full collaborator graph **eagerly in the constructor**, in dependency order — no lazy initialization. When fields depend on other fields, use a public `factory` constructor that assembles locals and hands them to a private constructor (see `VasterRuntime`). For closures needing `this`, a nullable field assigned in the constructor body is the only accepted fallback.
- **Owned Resources Unwind on Failure**: A constructor/factory that opens system resources (fds, mappings, processes) must close exactly what it opened on every failure path, and must not hold resources longer than needed (e.g. an fd is closed immediately after `mmap` — the mapping outlives it).

## 6. Conceptual Isolation Matrix (Concept Unawareness Rules)

To prevent concept conflation and architectural coupling across package boundaries, the following one-line concept unawareness rules are strictly enforced:

1. **AST Nodes & Frontend Constructs (`vaster_ast`, `vaster_domain`)**: Must NOT know about ISA bytecode execution, registers (`RegisterFile`), call stacks (`CallStack`), program counters (`_pc`), or low-level VM execution managers.
2. **ISA Bytecode & Opcodes (`vaster_instruction`)**: Must NOT know about AST frontend nodes, compiler implementation classes, host OS process handles, or host language object instances.
3. **LLM Models (`vaster_model`)**: Must NOT know about session history, context managers, tool dispatching loops, or opcode execution. Models are stateless inference processors.
4. **Sessions (`vaster_session`, `vaster_session_manager`)**: Must NOT know about tool call execution policies, maximum tool loop limits (`maxToolCallLoops`), or agent supervisor trees. Sessions are purely conversational memory and context heaps.
5. **Tools & Sandboxes (`vaster_tool`, `vaster_sandbox`)**: Must NOT know about LLM models, session conversation history, or ISA program execution state. Tools only map JSON inputs to JSON outputs.
6. **Agents & Supervisors (`vaster_agent`, `vaster_agent_manager_*`)**: Must NOT know about low-level ISA instruction decoding or program counter manipulation. Agents operate on model sessions, tasks, and tool managers.
7. **Security Policies (`vaster_policy`, `vaster_policy_engine`)**: Must NOT know about prompt text contents, model providers, or AST nodes. Policies strictly evaluate abstract actions against resource patterns.
8. **Continuations (`vaster_continuation`)**: Must NOT know about live socket handles, active model instances, host OS memory addresses, AST nodes (`vaster_ast`), domain specs (`vaster_domain`), or compiler classes (`vaster_compiler`). Continuations are pure serializable JSON snapshots of runtime execution state.
9. **Context Managers (`vaster_context`, `vaster_context_manager`)**: Must NOT know about tool execution, filesystem IO transactions, or agent supervisor trees. Context managers only shape token budgets and system instructions.
10. **Event Telemetry (`vaster_events`)**: Must NOT know how to mutate VM execution state, modify registers, or interrupt opcode dispatch. Telemetry is strictly passive and broadcast-only.
11. **Pricing (`vaster_pricing`)**: Must NOT know about sessions, context, or opcode execution. Rate tables live in the catalog, never in backend packages — backends only *measure* (wire-reported cost is measurement and belongs on `UsageMetadata`).
12. **Token Estimation (`vaster_token_estimate`)**: Must NOT know about quotas, budgets, or costs. Estimates are labeled (`UsageSource.estimated`) and centralized — no inline `~/ 4` heuristics anywhere else.
13. **Metering (`vaster_metering`)**: Every model call is metered through a `ModelCallMeter` — never hand-rolled charge sites. **One-owner event emission**: only the component that owns the model call publishes `ModelUsageEvent` (charge-only meters pass no event bus); per-turn events and task rollups are mutually exclusive.
14. **Agents Are Actors**: One agent = one session = one transcript = **one task at a time**. Same-agent tasks serialize FIFO through the agent's mailbox; concurrency exists only *across* agents. Components must never assume interleaved multi-task access to a single session.
15. **KV Contracts Are a Leaf; the MMU Is the Only Bridge**: `vaster_kv` (KvCacheHandle, KvCacheController, capabilities) must NOT know about context regions, context managers, or prompts — its transitive closure never reaches `vaster_context*` (enforced by `packages/model/vaster_kv/test/leaf_guard_test.dart`). The `ContextMmu` (`vaster_context_mmu`) is the single component aware of BOTH virtual context and physical KV state. Backend/model packages depend on the contracts, never on the bridge.

## 7. Dependency Addition Approval
- **Explicit User Approval Required**: ALWAYS ask for explicit user approval before adding any new dependency (production or dev_dependency) to any `pubspec.yaml` file across the workspace. Workspace-internal dependencies introduced by a user-approved plan are covered by that approval.

## 8. Machine State & Durability
- **No Loose State Fields on the Machine**: every piece of runtime machine state lives inside a named component implementing `MachineStateComponent` (`vaster_machine_state`), registered in `VasterRuntime._stateComponents` — the single enumeration point. Capture is a fold (`captureSnapshot`), restore is a dispatch (`restoreSnapshot`). Loose mutable fields on the runtime are forbidden: they are exactly how the first checkpoint silently lost the active session.
- **Descriptors Are State, Live Objects Never Are**: the active model is stored as its `ModelDescriptor` and resolved through the registry on use; cache hints are re-derived from restored pinned regions. Anything that cannot serialize is derived state by definition.
- **Carriers Do Not Enumerate Machine State**: `VasterContinuation` is identity + `MachineSnapshot`; `MachineCheckpoint` is program + continuation + VM-subsystem states + host-budget consumption. Neither lists machine components by name — a carrier cannot forget state it never enumerates.
- **Every Stateful VM Subsystem Exposes Export/Import in Its Own Package** (sessions, context regions, memory mounts, message inboxes) — none of them knows what a checkpoint is; `vaster_checkpoint` composes them all.
- **The Checkpoint-Anywhere Test Is the Gate**: capturing at every instruction boundary of the state gauntlet and resuming each into a fresh VM must reproduce the uninterrupted run. New machine or subsystem state must extend the gauntlet.
- **Snapshots Happen at Rest**: capture only at instruction boundaries (a paused/halted machine, or between `executeStep` quanta) — a capture mid-transition re-executes non-idempotent instructions on resume.

## 9. Shared-Memory Segment Protocols (`vaster_mmap`)
- **Compose Over the Two Building Blocks**: Every segment protocol (ring, frame, and anything future — KV pools, checkpoint segments) is a thin composition over `ShmSegment` (mapping lifecycle: create-vs-attach via `O_EXCL`, fd hygiene, owner-unlink-on-close) and `SegmentTag` (identity: magic + version as the first two header words). Never re-implement the open/attach/mmap ladder.
- **Ownership Is Discovered, Never Guessed**: `O_EXCL` decides creator vs attacher; only owners size and unlink by default; attach never creates. Validation happens against the header page before any payload byte is touched.
- **SPSC Honesty**: Rings are single-producer/single-consumer with documented publication order (payload before head, copy-out before tail, aligned 32-bit index words). Do not claim atomicity the platform does not provide; backpressure is typed (`RingFullException`), never silent overwrite.
- **KV Frames Carry Real State, Content-Addressed**: a KV frame's name derives from the source content's fingerprint; its payload is engine state *derived from* that content (provenance addressing — byte equality of payload and preimage is not implied). Frames are allocated at exact state size and filled before publication (`allocate` + `payloadPointer`); the inference engine's own state versioning is the compatibility authority — a rejected restore is a typed error (`LlamaStateIncompatibleException`), never a silent cold start.
- **Transports Never Fabricate Success**: an unanswered or failed IPC request is a typed error (`SidecarUnavailableException`, `SidecarRemoteException`, and error envelopes on the wire) — a transport that fakes a response hides real races (the half-duplex self-consumption bug lived undetected behind exactly such a stub). Post-close operations on mapped structures are typed errors, not native faults.
- **No Dart Trampolines for Process-Global Native Callbacks**: a callback registered process-wide that native code may invoke from any thread at any time (e.g. llama's log callback) must never point at a Dart `NativeCallable` — the trampoline dangles when its installing isolate dies. Point it at a permanently-valid native no-op instead (see `LlamaBindings.silenceLogs`).

## 10. Placement Law — Where Logic Lives

When code could live in two places, these rules decide. The tiebreak behind all of them: put logic where its dependencies are narrowest and where a second implementation would reuse it unchanged.

1. **Contracts & Formats Live in Leaves, Beside What They Govern**: interface contracts and the binary/wire formats that realize them live together in leaf packages (`KvCacheController` + `KvStateImage` in `vaster_kv`; the ISA + VBC codec in `vaster_instruction`; `vaster_vm_api`). Formats are **container-agnostic and language-agnostic**: specified in `docs/specs/` with normative semantics, anchored by committed golden-byte fixtures a second-language implementation must reproduce. A format never lives in a transport package — transports carry formats, they do not own them.
2. **Transports Move Bytes, Nothing Else**: transport/container packages (`vaster_mmap`, `vaster_model_rpc`) own byte movement, container framing, and transport-object naming (`kvFrameName`) — never domain validation, never policy, and never fabricated success (Rule 9). A transport host serves interfaces, not concrete backends (`RingSidecarHost` takes any `VasterModel`).
3. **Engines Own Policy; Workers and Hosts Marshal**: algorithmic/policy code (generation loops, prefix-reuse decisions, validation) lives in the engine class of its backend package (`LlamaEngine`); isolate workers, sidecar hosts, and dispatch tables are pure marshalling. Two copies of a loop is a defect, not a style choice.
4. **Semantic Validation Lives With the Engine That Owns the Semantics**: token-exact prefix validation, state-compatibility checks, and their kin execute wherever the engine is — sidecar-side in a ring topology — never inside a transport and never on the engineless side of a wire. For content-addressed hosted backends the server's exact-prefix matching *is* that validation; adapters must not duplicate it.
5. **Bridges Are Dedicated Packages and the Only Two-Sided Components**: a component whose job requires knowing two layers is its own package (`vaster_context_mmu`, `vaster_checkpoint`) and is the *single* place that knowledge exists. The layers it bridges stay leaves; load-bearing leaf-ness is enforced by a guard test (`packages/model/vaster_kv/test/leaf_guard_test.dart`), not by memory.
6. **Hosts Own Composition and the Lifecycle of What They Spawn**: backend construction has one owner (`backend_resolver`, which also owns `dispose` for resources it acquires); park-time orchestration (checkpoint files, KV prewarm) is host policy — the runtime stays unaware of both. Host code may know everything; nothing may know the host.

## 11. Declarative Signatures — Results Over Side Effects (REVIEW RULES)

Two standing review rules. Every review flags violations in NEW or CHANGED code; existing surfaces migrate opportunistically when touched, never big-bang.

- **`void` Is a Smell — Operations Return What They Did**: a `void` return says "trust me, something happened" — imperative mutation with no composable result. New and changed APIs return the value they produced, the state they transitioned to, a typed receipt/handle, or the outcome hierarchy of what happened: parsers return values, mutations return the resulting entity or a delta, registrations return handles/disposers, `commit`-style operations echo what they committed so callers compose (`recorded ?? commit(claim, await execute())`). This is how a declarative, reactive frame keeps OOP's strengths: objects with behavior whose every operation yields data the next operation can consume. Sanctioned terminal sinks — the places a result genuinely has no consumer — are already law elsewhere and stay `void`: broadcast-only telemetry publish (Rule 6.10) and `MachineStateComponent.restoreState` dispatch (Rule 8). A new `void` outside those must justify itself in review or return its result.
- **Strings Carry Data, Never Semantics**: a `String` that callers branch on, compare against constants, prefix-match, or pass as a mode/kind/state is a missing type. Model it: a **sealed hierarchy** when variants carry data (`TaskOutcome`, `DecisionOutcome`), an **enum** when they don't (`UsageSource`, `RuntimeStatus`), a **const value class** when it is a validated identity or format (`ModelDescriptor`, not `"provider:id"` split at call sites; codecs per Rule 2, not inline parsing). Wire/ABI strings are the ONE sanctioned string domain (Rule 1 — the ISA's language-agnostic surface: opcode names, register names, descriptor keys, outcome `kind`s), and the boundary discipline is: parse into the typed form at the edge, once, in a const-constructible codec/value class — semantics never travel as strings *inside* a layer. The P2 lesson is canonical: the policy-violation "type check" was a string prefix match until it became `PolicyViolationException`; reviews hunt for the same shape everywhere.
